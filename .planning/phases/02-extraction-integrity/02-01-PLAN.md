# PLAN 02-01 — Extraction pipeline + integrity layer

## Objective

Wire the extraction pipeline into the upload flow: every ingested artifact gets entity extraction (spaCy PERSON/ORG + regex PHONE/EMAIL/IP/URL), images get Tesseract OCR + EXIF metadata, and every artifact gets an immutable SHA-256 plus an append-only chain-of-custody log. Corrupt/unsupported uploads fail gracefully with a clear message and persist nothing.

## Wave 1 — tracer slice (must verify before Wave 2)

### Task 2.1 — Extraction service: entities from text, wired into upload
- **read_first:** `apps/api/app/models.py`, `apps/api/app/main.py`, `phases/02-extraction-integrity/02-CONTEXT.md`, `.planning/research/STACK.md` (§5)
- **action:**
  1. Create `apps/api/app/services/extraction.py` with `extract_text_artifact(text, artifact_id) -> list[Entity]`: spaCy `en_core_web_sm` for PERSON/ORG + regex extractors for PHONE (Indian 10-digit + `+91`), EMAIL, IP (v4), URL. Each entity: `{kind, value, span_json: {start, end}}`.
  2. Wire into `POST /api/artifacts`: after storing the artifact, run the text extractor for `document`/`chat`/`log` source types and bulk-insert rows into `entities`.
  3. Add `spacy==3.8.16` to `apps/api/requirements.txt`; Dockerfile runs `python -m spacy download en_core_web_sm` at build time.
  4. Add `GET /api/artifacts/{id}` returning the artifact with its `entities` array (this endpoint does not exist yet — Phase 1 only built the list endpoint).
  5. Create fixture `apps/api/tests/fixtures/chat_sample.txt` (WhatsApp-style export with 2 persons, 1 phone, 1 email, 1 IP).
- **verify:** Upload the fixture via the API, then `GET /api/artifacts/{id}` returns the artifact with an `entities` array; a python check asserts at least the phone and both person names are present with correct `kind`.
- **acceptance_criteria:**
  - Uploading `chat_sample.txt` yields ≥4 entity rows in the `entities` table with `artifact_id` set, kinds among PERSON/PHONE/EMAIL/IP/URL, and `span_json` offsets that slice the expected substrings from the source text.
  - The spaCy model loads from the image build (no runtime download — check Dockerfile layer, not network at container start).

### Task 2.4 — Chain-of-custody log + hash immutability
- **read_first:** `apps/api/app/models.py`, `phases/02-extraction-integrity/02-CONTEXT.md` (custody vocabulary)
- **action:**
  1. Add `custody_log` table per 02-CONTEXT.md; helper `log_custody(artifact_id, action, detail)`.
  2. Log `ingest` on upload, `extract` after extraction, `view` on `GET /api/artifacts/{id}` (actor `"investigator"`).
  3. Add `GET /api/artifacts/{id}/custody` returning entries newest-first.
  4. Immutability: no code path updates `artifacts.sha256` after insert (assert by grep — zero `UPDATE artifacts SET sha256` occurrences).
- **verify:** Upload a file, view it once, then `GET .../custody` shows `ingest`, `extract`, `view` entries in order with UTC ISO timestamps.
- **acceptance_criteria:**
  - Custody endpoint returns the three entries in chronological order; `grep -rn "sha256" apps/api/app --include=*.py | grep -i update` returns nothing.

### Task 2.5 — Graceful failure for unsupported/corrupt files + artifact detail UI
- **read_first:** `apps/api/app/main.py` (upload handler), `apps/web/src/app/page.tsx`
- **action:**
  1. Upload handler: extension allowlist per source type + try/except around parsing; on failure return HTTP 422 `{"detail": "<clear reason>"}` and delete any partial file/row (nothing persisted).
  2. Web UI: surface the 422 message inline; extend the artifact list so clicking a row opens an artifact detail view showing metadata, SHA-256, extracted text, EXIF, entities, and custody entries.
- **verify:** `curl` upload of a zero-byte `.png` and a `.exe` renamed `.txt` → both 422 with a `detail` message; DB row count unchanged afterward. UI detail view renders for a good artifact.
- **acceptance_criteria:**
  - Both bad uploads return 422 with human-readable `detail`; `SELECT COUNT(*) FROM artifacts` is identical before and after.
  - Artifact detail page shows all six sections (metadata, hash, text, EXIF, entities, custody) for a valid artifact.

### Task 2.7 — OSINT web collection (ING-04)
- **read_first:** `apps/api/app/main.py`, `apps/api/app/services/extraction.py`, `phases/02-extraction-integrity/02-CONTEXT.md` (OSINT decision)
- **action:**
  1. Add `scrapling` to `apps/api/requirements.txt` (HTTP Fetcher surface only — no Playwright/browser extras in v0.1).
  2. Create `apps/api/app/services/osint.py`: `fetch_url(url) -> {markdown, final_url}` using Scrapling's `Fetcher` with `robots_txt_obey=True`, 15 s timeout, desktop user-agent; `search_news(keyword, limit=5) -> list[url]` via Google News RSS.
  3. Add `POST /api/osint/fetch` accepting `{url}` or `{keyword}`: fetch the page(s) → store each as an artifact with `source_type="osint"`, cleaned Markdown as the artifact text, `metadata_json={url, fetched_at_utc, fetcher: "scrapling-http"}` → run the standard text extraction pipeline over it so entities land in `entities`.
  4. Fetch failures (DNS/timeout/HTTP ≥400/robots disallow) → HTTP 422 `{"detail": "<reason>"}`; nothing persisted.
  5. Web UI: an "Add web source" input (URL or keyword) on the upload page posting to the new endpoint.
- **verify:** `POST {"url": "<stable test page>"}` → artifact with `source_type="osint"`, `metadata_json` containing url + fetch timestamp + fetcher id, and entities extracted; `POST {"url": "<known 404>"}` → 422 and artifact row count unchanged; `POST {"keyword": "test"}` → ≥1 artifact from RSS results (if offline, logs a skip note instead of failing).
- **acceptance_criteria:**
  - A fetched page yields an `osint` artifact whose `metadata_json` contains the URL, fetch timestamp, and fetcher id, with entities extracted from its text.
  - Blocked/failed fetches return 422 with a human-readable reason and persist nothing.

## must_haves

- `apps/api/app/services/extraction.py` exists with entity extraction, OCR, EXIF functions.

- `custody_log` table exists; `artifacts` has `extracted_text` and `exif_json` columns (schema extended, not redesigned).

- `POST /api/osint/fetch` works for URL and keyword inputs; `osint` artifacts carry URL + fetch timestamp + fetcher id in `metadata_json` and flow through the standard extraction pipeline.
- spaCy model + Tesseract are baked into the API image (Dockerfile), never downloaded at runtime.
